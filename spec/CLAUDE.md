# code 文件夹最高规则入口

## 角色定位

- 解读当前文件夹下的代码框架结构s
- 对工程进行合理的代码编写

## 持久化规则

- 对话和输出文件的内容首选中文（除特殊要求）
- 当对话中出现「解读」「解释」「分析」「了解」等意思相近的关键词时，将结果直接以 Markdown 形式输出到**默认文件夹**中
- 如果有直接的输出路径要求，就再复制一份

### 文件命名规则

| 输出目录         | 命名格式                            |
| ------------ | ------------------------------- |
| `/doc`       | `{工程名}-architecture.md`         |
| `/knowledge` | `{工程名}-{关键技术}.md`               |
| `/plan`      | `{yyyy-mm-dd}-{工程名}-{计划的摘要}.md` |
| `/spec`      | `{工程名}-design.md`               |

### 图表规范

- 输出 Markdown 文档中的架构图/流程图，**禁止使用 ASCII box-drawing 字符**（`┌─┐│└┘├┤` 等）绘制含中文文本的框图——中文字符在终端中占 2 列宽度而框线字符占 1 列，会导致右侧边框严重错位
- 替代方案：优先使用 **Mermaid** 流程图（`flowchart TD`），Obsidian 原生支持渲染，不受字符宽度影响
- 简单的流程线（如 `A → B → C`）可直接用纯文本箭头，无需框图

## 编码规则

**权衡说明**：以下规则偏向谨慎而非速度。对于简单任务可以灵活判断。

### 1. 先思考再编码

**不要假设，不要隐藏困惑，主动暴露权衡。**

在动手实现之前：
- 明确陈述你的假设。如果不确定，先问。
- 如果存在多种理解方式，全部展示出来——不要默默选一种。
- 如果存在更简单的方案，直接说。必要时可以坚持己见。
- 如果有不清楚的地方，停下来。说清楚哪里困惑，提问。

### 2. 简洁优先

**用最少的代码解决问题，不写任何推测性内容。**

- 不做需求之外的功能。
- 不为单次使用的代码建立抽象层。
- 不做没有被要求的"灵活性"或"可配置性"。
- 不为不可能发生的场景写错误处理。
- 如果写了 200 行而 50 行就能搞定，重写它。

问自己：「资深工程师看到这个会说过度设计吗？」如果是，就简化。

### 3. 精准修改

**只动必须动的。只清理自己制造的混乱。**

编辑已有代码时：
- 不要"顺便优化"相邻的代码、注释或格式。
- 不要重构没坏的东西。
- 匹配现有代码风格，即使你倾向于另一种写法。
- 如果发现不相关的死代码，提出来——但不要直接删。

当你的修改造成孤立的残留：
- 删掉**你的修改**造成的不再使用的 import / 变量 / 函数。
- 不要删除已有的死代码，除非被要求。

测试标准：每一行改动都应该能直接追溯到用户的需求。

### 4. 目标驱动执行

**定义成功标准，循环迭代直到验证通过。**

把任务转化为可验证的目标：
- "加校验" → "先给非法输入写测试，再让测试通过"
- "修 bug" → "先写能复现它的测试，再让测试通过"
- "重构 X" → "确保重构前后测试都通过"

对于多步骤任务，先给出简要计划：
```
1. [步骤] → 验证: [检查项]
2. [步骤] → 验证: [检查项]
3. [步骤] → 验证: [检查项]
```

强的成功标准让你能独立迭代。弱的标准（"搞出来就行"）会需要不断追问澄清。

---

**这些规则生效的标志是**：diff 中不必要的改动变少、因过度设计导致的重写变少、澄清性问题在实现之前提出而非在出错之后。
